Respuestas a vuestras 2 preguntas:


3.1) chatGroup members → OPCIÓN (a): sessionIds basta
---------------------------------------------------------

Hemos auditado el código del front. Lo que llamábamos "members" del chatGroup son AGENTES (LobeChat es multi-agente), NO usuarios con rol. Las APIs del store son:

  - addAgentsToGroup(groupId, agentIds[])
  - removeAgentFromGroup(groupId, agentId)
  - reorderGroupMembers(groupId, ordering[])

Es decir, una colección de agentes (o sessions) por grupo. NO hay rol asociado.

Por tanto: nos vale gestionar `sessionIds[]` o `agentIds[]` vía:

  PATCH /chat/session-groups/{id}
  body: { sessionIds: ["sess_xxx", "sess_yyy"] }

NO necesitamos modelo nuevo `ChatGroupMember` en api-mcp. Lo descartamos.

  → Acción: ningún endpoint nuevo. Documentamos en el front que se gestiona
    como sessionIds. Si en el futuro surge necesidad real de "usuarios con
    rol en un grupo" (multi-tenant chat compartido entre usuarios humanos),
    abriremos ticket separado.


3.4) image CRUD → NO necesitamos GET/DELETE /api/images/{id} dedicado
----------------------------------------------------------------------

Auditamos uso real en producción del front:

  imageService.createImage()  → 2 call-sites (store action de createImage)
  imageService.getImageItem() → 0 call-sites en producción
  imageService.removeImage()  → 0 call-sites en producción

Es decir, la "interfaz CRUD" del servicio existía por inercia tRPC pero NO se usa. Solo `createImage` que ya tenéis cubierto con /webapi/text-to-image/{provider}.

  → Acción: NO pedimos endpoint nuevo. Si en el futuro hace falta CRUD por id,
    tratamos Image como File usando vuestros /api/storage/files/{id} y
    /api/storage/r2/files (cuando los expongáis).

3.6.5) chatGroup agents con order/role — corrección a 3.1

Re-auditando el código del front: además de la lista de agentes en el grupo,
existe una tabla de relación `chatGroupAgents` con campos extra:

  ChatGroupAgent { groupId, agentId, order: number, role: string }

  - addAgentsToGroup(groupId, agentIds[])    crea registros con order auto
  - removeAgentsFromGroup(groupId, agentIds[])
  - updateAgentInGroup(groupId, agentId, { order, role })
  - getGroupAgents(groupId): ChatGroupAgent[]

Esto significa que con `{ sessionIds: [...] }` plano (sin order ni role) NO
basta. Queremos gestionar order y role por agente en el grupo.

¿api-mcp expone (o puede exponer) este metadato extra (order, role) por
agente del grupo? Si NO:

  (a) deprecamos order y role del front (los grupos pasan a ser un array
      simple sin metadato) — simplifica UI
  (b) abrimos ticket a api-mcp para incluir order+role en el modelo
      ChatGroupAgent (similar a thread, requiere modelo nuevo)

Confirmadnos y movemos chatGroup en consecuencia.

Hoy esos métodos persisten en pglite/drizzle del front (lo que vamos a eliminar). ¿Cuál es el plan para CRUD de plugins instalados:
