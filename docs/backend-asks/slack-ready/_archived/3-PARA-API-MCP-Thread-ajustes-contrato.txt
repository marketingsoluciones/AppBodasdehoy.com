4 AJUSTES SOLICITADOS AL CONTRATO GraphQL Thread
═══════════════════════════════════════════════════════════

[1] enum type — usar el del front, NO el que propusisteis

  Vuestro contrato:    type: String! = "branch"|"followup"|"clarification"|"summary"
  Front actual:        type: ThreadType = "continuation"|"standalone"
  Schema drizzle:      packages/database/src/schemas/topic.ts (existe desde origen LobeChat)

  Motivo: el front ya tiene store/UI/i18n/tests sobre estos 2 valores. Los
  4 que propusisteis son taxonomía de "tipo de pregunta" que el usuario
  no elige conscientemente — son metadatos sin UX.

  SOLICITUD:
    enum ThreadType {
      Continuation   # thread continúa la línea del topic principal
      Standalone     # thread arranca tema aparte colgando del message
    }
    type Thread { ... type: ThreadType! ... }


[2] enum status — `'deprecated'` en vez de `'closed'`

  Vuestro contrato:  status: String! = "active"|"archived"|"closed"
  Front actual:      ThreadStatus = "active"|"archived"|"deprecated"

  Motivo: el front ya tiene este enum en schema drizzle desde origen.
  Cambiar a 'closed' rompe migraciones y selectors.

  SOLICITUD:
    enum ThreadStatus { Active Archived Deprecated }
    type Thread { ... status: ThreadStatus! ... }


[3] createThreadWithMessage — usar el SendMessageInput existente

  Vuestro contrato:  message: MessageInput! (sin definir cuál)
  Lo que ya usamos:  sendMessage(sessionId: String!, input: SendMessageInput!)
                     en graphql_proxy.py:692 y rest_chat_handler.py:6155/6412

  Motivo: si MessageInput es un type nuevo, duplica validación y diverge
  del flujo sendMessage. Mejor reusar el contrato existente — solo
  añadimos topicId/threadId en el contexto.

  SOLICITUD:
    input CreateThreadWithMessageInput {
      title: String
      type: ThreadType!
      sourceMessageId: ID
      parentThreadId: ID
      message: SendMessageInput!     ← reusar el de sendMessage
    }


[4] type Thread.type como ENUM tipado, NO String!

  Vuestro contrato:  type: String!
  Mejor:             type: ThreadType! (enum GraphQL nativo)

  Motivo: con String! el schema GraphQL no valida valores → permite enviar
  basura desde cualquier cliente. Un enum tipado da validación gratis +
  introspección + autocomplete en clients generados (codegen).

  Aplica también a status (= ThreadStatus! en vez de String!).
