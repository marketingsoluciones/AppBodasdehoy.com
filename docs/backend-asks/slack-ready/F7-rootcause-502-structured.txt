BUG #1 — 502 en /chat/structured (provider/key mismatch)
═══════════════════════════════════════════════════════════

Reproducción exacta:
  POST /chat/structured
  body: {messages, schema, model:"gpt-4o-mini", provider:"openai"}
  header: X-Development: bodasdehoy

Trazas log (Jun 06 14:48:37 UTC):

  INFO:rest_chat_handler:📋 Obteniendo modelos para
       provider=openai, development=None, trace_id=...
  INFO:core.whitelabel_config:🔍 Obteniendo ai desde MCP_GRAPHQL
       para bodasdehoy
  ...whitelabel resolver devuelve aiApiKey = "gsk_s8t7…CQMo"
       (que es la GROQ key del whitelabel, no la OpenAI)
  ...api-ia instancia OpenAIProvider con esa "gsk_" key
  ...OpenAI API rechaza:
     openai.AuthenticationError: 401
       "Incorrect API key provided: gsk_s8t7…CQMo"

  File: services/ai/providers/openai.py:67  → llamada falla
  File: services/ai/providers/openai.py:90  → except levanta
        Exception(f"API key inválida: {e}")
  Exception genérica no manejada por FastAPI
  → "POST /chat/structured HTTP/1.0" 502 Bad Gateway

Causa raíz:
  El whitelabel `bodasdehoy` en MCP tiene UN solo campo
  `aiApiKey` = "gsk_…" (Groq). Cuando el cliente pide
  provider:"openai" EXPLÍCITAMENTE, el resolver actual
  devuelve esa MISMA key Groq como si fuera de OpenAI.

Solución (2 opciones):
  A) Multi-provider en whitelabel — añadir campos:
     aiApiKey_openai, aiApiKey_anthropic, aiApiKey_groq…
     Resolver: pick by requested provider.

  B) Fallback a .env — si la key del whitelabel no coincide
     con el provider pedido, usar .env (el log dice que
     OpenAI/Anthropic ya tienen keys en .env del backend).

     Vi: "Usando credenciales del .env como fallback / Anthropic
     key válida desde .env / OpenAI key válida desde .env"
     (línea 14:48:24 del log)
     → el fallback EXISTE para /webapi/models, falta aplicarlo
       a /chat/structured.

  C) Mientras tanto, FastAPI debería devolver 401 (auth error),
     no 502 — para que el cliente sepa que es problema de key.
