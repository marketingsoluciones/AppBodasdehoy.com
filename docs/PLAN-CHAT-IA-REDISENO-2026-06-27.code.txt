## TL;DR

Reorganización del producto chat-ia en torno a 3 ejes:

  EJE 1. PERFORMANCE: 1 SSE singleton + cache compartido + sync multi-device
  EJE 2. UX: eliminar duplicación Bandeja A vs B sin perder funcionalidad
  EJE 3. CONCEPTO: distinguir CHAT IA vs CONVERSACIÓN MENSAJERÍA + multi-canal

Apps actuales que comparten infra:
  · chat-ia (PRINCIPAL — este plan)
  · appEventos (link entrante via SSO)
  · memories-web (link entrante via SSO)
  · editor-web (link entrante via SSO)

Tiempo estimado total: 4-6 sprints (variable según opción rediseño elegida).

PLAN A — SSE SINGLETON + MULTI-DEVICE SYNC + CACHE
═══════════════════════════════════════════════════════════════════════════════

PROBLEMA REAL CONFIRMADO
─────────────────────────────────────────────────────────────────────────────

QA + análisis Bandeja /chat vs /messages detectó:
  · 4 conexiones SSE simultáneas a /api/messages/stream
  · 5x GET /whatsapp/session, 3x GET /conversations duplicados
  · Notificaciones potencialmente disparadas 4 veces
  · Memory leak de SSE no cerrados al cambiar de ruta
  · Múltiples instancias del mismo store sin sync

CAUSAS RAÍZ
─────────────────────────────────────────────────────────────────────────────

  1. useUnifiedFeed.ts abre EventSource directo
  2. useMessageStream.ts abre OTRO EventSource al mismo endpoint
  3. useRecentConversations.ts hace fetch sin SWR cache compartido
  4. useConversations.ts duplica el fetch
  5. useWhatsAppSession.ts llamadas redundantes a /session
  6. Bandeja A en /chat sidebar usa hooks independientes de Bandeja B

PROPUESTA ARQUITECTURA 3 CAPAS
─────────────────────────────────────────────────────────────────────────────

CAPA 1 — Backend api-ia (cambios mínimos, lo principal ya existe)
  Endpoint: GET /api/messages/stream (YA EXISTE)
  Nuevo: Redis Pub/Sub o similar pub/sub interno
    · Webhooks externos (WhatsApp, FB, IG, web chat) publican en
      canales `tenant:{development}:conv:{conv_id}`
    · SSE handler subscribe a los canales que el user tiene permiso
  Filtrado server-side por:
    · auth JWT
    · scope evento (linkedEventId) o brand (development)
    · viewer permissions de la conversación
  Eventos:
    {type: "new_message", convId, message: {...}}
    {type: "conv_updated", convId, fields: {...}}
    {type: "notification", notif: {...}}
    {type: "typing", convId, userId, ttl: 3000}
    {type: "read_receipt", convId, msgId, readByUserId}

CAPA 2 — Frontend store unificado (NUEVO)
  Archivo: apps/chat-ia/src/store/bandeja/index.ts

  interface BandejaStore {
    // Datos
    conversations: Record<string, Conversation>;
    notifications: Notification[];
    unreadCounts: { byChannel: Record<string, number>, total: number };
    typingByConv: Record<string, { userId: string; expiresAt: number }[]>;

    // SSE singleton
    _sseConnection: EventSource | null;
    _sseRetryTimer: ReturnType<typeof setTimeout> | null;

    // BroadcastChannel singleton (cross-tab sync)
    _broadcastChannel: BroadcastChannel | null;
    _isLeaderTab: boolean;

    // Actions
    initBandeja: () => Promise<void>;  // 1 fetch inicial REST
    initSSE: () => void;               // singleton
    closeSSE: () => void;
    sendMessage: (convId: string, content: string) => Promise<void>;
    markAsRead: (convId: string, msgId: string) => Promise<void>;
    // ... etc
  }

  Comportamiento:
    · initBandeja() corre 1 SOLA VEZ al login (REST + cache SWR 30s)
    · initSSE() abre 1 EventSource singleton, todos los componentes
      consumen del store NO abren sus propios SSE
    · BroadcastChannel "bandeja-events" sincroniza tabs del mismo browser
    · Leader election: localStorage.setItem("bandeja-leader", tabId)
      con timestamp. Si timestamp > 5s atrás, otra tab toma el rol.
    · Retry SSE con exponential backoff (1s, 2s, 4s ... max 60s)
    · Si user offline: cola de mensajes pendientes en localStorage,
      al volver online → POST /messages/batch + resync via REST

CAPA 3 — Migration plan
  Sustituir hooks existentes uno por uno por selectores del nuevo store:
    useUnifiedFeed → useBandejaStore(items)
    useRecentConversations → useBandejaStore(conversations)
    useConversations → useBandejaStore(conversations[channel])
    useMessageStream → useBandejaStore(messagesOf(convId))
    useWhatsAppSession → useBandejaStore(waSession[development])

  Backward compat:
    Mantener los hooks viejos como wrappers temporales que delegan al
    store, marcados @deprecated. Migrar componente por componente.
    Eliminar wrappers cuando 0 callsites.

PROBLEMA CONCEPTUAL ACTUAL
─────────────────────────────────────────────────────────────────────────────

La palabra "chat" se usa para 2 cosas distintas:
  1. CHAT IA — conversación user ↔ agente IA (lo que LobeChat hacía)
  2. CHAT MENSAJERÍA — conversación user ↔ otro humano (WhatsApp, etc.)

Esto confunde a:
  · Usuarios ("¿dónde está la bandeja del Facebook?")
  · Devs ("¿el endpoint /chat es para IA o para mensajería?")
  · Stakeholders ("estamos hablando de chat o de bandeja?")

NOMENCLATURA PROPUESTA (negocio + producto)
─────────────────────────────────────────────────────────────────────────────

  PALABRA NUEVA            SIGNIFICADO
  ──────────────────────  ──────────────────────────────────────────
  ASISTENTE                Sustituye "Chat IA". Es tu agente IA.
                          Ruta: /asistente (antes /chat)

  CONVERSACIÓN             Mensaje con otro humano vía cualquier canal.
                          La unidad atómica del mensaje persona ↔ persona.
                          Plural: "Conversaciones".

  BANDEJA                  Inbox unificado de todas las conversaciones.
                          Ruta: /bandeja (antes /messages).

  CANAL                    Origen del mensaje: WhatsApp, Email, Web Chat,
                          Facebook, Instagram, Llamada, SMS, etc.

  HILO                     Mensajes encadenados dentro de una conversación.
                          NO confundir con "Topic" del asistente IA.

  AGENTE                   2 acepciones (a clarificar en UI):
                          a) Agente IA: tu IA. Sigues hilo de conversación
                             con TU agente IA.
                          b) Agente humano: quien atiende conversaciones
                             desde tu equipo (organizador, planner, etc.)

  CONTACTO                 Persona única identificada en CRM. Puede
                          aparecer en N conversaciones cross-canal +
                          cross-evento.

ANALOGÍAS DE OTROS PRODUCTOS DEL SECTOR
─────────────────────────────────────────────────────────────────────────────

  Intercom usa: "Inbox" + "Conversations" + "Operator" (IA)
  Front usa:    "Inbox" + "Conversations" + "Front" (asistente IA)
  Crisp usa:    "Inbox" + "Conversations" + "MagicReply" (IA)
  Zendesk usa:  "Tickets" (más enterprise)
  Helpscout:    "Mailbox" + "Conversations"
  Tidio usa:    "Conversations" + "Lyro" (IA)

  Patrón sector: Inbox(=Bandeja) + Conversations(=Conversaciones) +
                  nombre propio para IA.

CASO REAL que el usuario mencionó:
  Carmen llama por WhatsApp al número corporativo de Bodas de Hoy.

  Sistema actúa:
    1. Crea CONVERSACIÓN nueva, canal=whatsapp, linkedEventId=null
    2. Busca CONTACTO existente con phone=+34... Si NO existe → crea
       nuevo (rol=lead_marca, sin evento).
    3. La conv aparece en BANDEJA con scope=marca (no evento).
    4. Más tarde se descubre que Carmen es INVITADA de Boda Isabel & Raúl:
       · Sistema mantiene contacto único Carmen
       · Conv WhatsApp se mantiene scope=marca (la inició como lead)
       · Conv NUEVA cuando Carmen interactúe sobre la boda concreta
         (ej. confirmar asistencia vía link RSVP) → linkedEventId=Boda...
    5. UI muestra "Carmen" con tabs:
       · Marca (1 conv abierta)
       · Boda Isabel & Raúl (1 conv RSVP)
       · Cualquier otro evento donde aparezca

PATRÓN COMÚN del sector
─────────────────────────────────────────────────────────────────────────────

  Vista lista conversaciones (izquierda) + thread (centro) + sidebar
  info contacto (derecha). 99% de productos siguen este patrón. Nuestro
  rediseño debe respetarlo.

  Canales se diferencian con BADGES no con listas separadas.
  Scope (evento/marca/etc) es un FILTRO no una vista distinta.

  IA aparece como sugerencia EN la conversación (no como app aparte).

PLAN DE REDISEÑO — modo de trabajo
═══════════════════════════════════════════════════════════════════════════════

OPCIÓN A — Componente a componente (incremental, riesgo bajo)
─────────────────────────────────────────────────────────────────────────────

  Sprint 1 (1 sem): Bandeja unificada — store + SSE singleton + cache
                    sin tocar UI
  Sprint 2 (1 sem): Eliminar Bandeja A tras inventario
  Sprint 3 (1 sem): Renombrar /chat → /asistente + /messages → /bandeja
                    (con redirects 301)
  Sprint 4 (1 sem): Modelo Contacto + roles cross-evento (DB + API)
  Sprint 5 (1 sem): UI ScopeSelector mejorado + filtros canal
  Sprint 6 (1 sem): Iconografía nueva + microinteracciones
  Sprint 7+ (1 sem): Polish + analytics + métricas SLA

  Pros: cada sprint es deployable independiente, riesgo controlado
  Cons: tarda 7+ semanas en ver "el después" completo

OPCIÓN B — Rediseño global con prototipo paralelo (riesgo medio)
─────────────────────────────────────────────────────────────────────────────

  Paso 1: Diseñador (humano o IA) hace mockups Figma de cómo quedaría
          la app COMPLETA tras rediseño. 3-5 días.
  Paso 2: Front (yo) implementa un nuevo grupo (group) en Next.js
          (main-v2) con todas las rutas nuevas + nuevos componentes,
          SIN tocar el (main) actual. Esto es "behind feature flag".
  Paso 3: Activar /v2 para usuarios beta. Mantener /v1 paralelo.
  Paso 4: Telemetría compara v1 vs v2 (engagement, tickets).
  Paso 5: Si v2 gana → swap default. Si v1 gana → ajustar v2 hasta que
          gane o descartar.

  Pros: ves el "después" completo antes de borrar lo viejo, A/B testing real
  Cons: doble carga de mantenimiento durante el periodo paralelo

OPCIÓN C — Mock interactivo en Storybook + Figma (más rápido para validar)
─────────────────────────────────────────────────────────────────────────────

  Paso 1: Figma con todas las pantallas rediseñadas (1 semana diseñador)
  Paso 2: Storybook con componentes nuevos vivos (1 semana front)
  Paso 3: Usuario clickea por el Storybook, prueba el flujo SIN datos
          reales, valida UX
  Paso 4: Decisión "Adelante" → empezar opción A o B con confianza

  Pros: validación temprana sin tocar producción, barato
  Cons: solo valida UX, no integración real con backend

RECOMENDACIÓN
─────────────────────────────────────────────────────────────────────────────

OPCIÓN B (rediseño paralelo) es la mejor para tu caso porque:
  · Quieres ver "antes y después" de la app
  · Quieres PROBAR opciones antes de comprometer
  · El rediseño es grande (nomenclatura + modelo conceptual + UI)

Pero antes hacer OPCIÓN C abreviada:
  · 2-3 días de mockup HTML estático del "después"
  · Tú lo ves, eliges 1 dirección
  · Después empezamos B con esa dirección clara
