⚠️ #2 BUG-CW-N15 — aclaración con datos del front
══════════════════════════════════════════════════════════════════════

Razón: tenéis razón, mi hipótesis "no filtra por X-Development" era falsa.
Os reporto lo que SÍ hace el front para que delimitemos al backend:

(a) FILTROS ENVIADOS:
  · Badge (NotificationBell.tsx:107):
      getNotifications(20)  →  (limit=20, unreadOnly=false, page=1)
      → notifications.ts:91  →  filters = undefined  (NO read:false)
      → query GraphQL: getNotifications(filters: null, pagination: {limit:20, page:1})

  · getUnreadNotificationsCount (badge directo):
      Sin filtros, sin variables, query escalar Int.

  · Panel /notifications/page.tsx (otra ruta, no es el badge):
      Estado inicial: filter='all', typeFilter=null
      → getNotifications(30, false, 1)  →  filters = undefined
      → query con limit:30
      Solo cuando el usuario PINCHA "Solo no leídas" pasa a unread → filters={read:false}.

  CONCLUSIÓN: el front NO está enviando filters.read=true ni typeFilter
  cuando se abre el badge. Si vuestro logging dice lo contrario, capturadme
  el trace_id concreto y os mando JWT + repro paso a paso.

(b) USUARIO IDENTIFICADO EN JWT:
  apps/chat-ia/src/services/firebase-auth/index.ts:146,173,216,264 →
    userId: user?.email || user?.uid

  Esto significa que el JWT lleva `userId = bodasdehoy.com@gmail.com` (email)
  para super-admin, no firebase_uid. Mismo JWT para ambas queries
  (mismo mcpClient, mismo header Authorization).

  HIPÓTESIS para vuestro side: si `getUnreadNotificationsCount` resuelve el
  usuario por `payload.sub` o `payload.uid` y `getNotifications` lo
  resuelve por `payload.email` (o viceversa), las dos consultas mirarían
  campos distintos del JWT → mismatch.

  Para validar: en vuestros resolvers, hacer un log temporal con
    `console.log(field_used, resolvedUserId)` en ambos resolvers
  con el mismo JWT y comparar. Si difieren, ese es el bug.

(c) DEV ENVIADO:
  Header `X-Development: bodasdehoy` (mcpClient.ts:7-12). Mismo header en
  ambas queries. Si vuestro resolver A lo recibe correctamente y B no, es
  middleware/context inconsistente entre resolvers.

PROPUESTA: si encontráis que el campo es distinto entre resolvers, lo más
seguro es unificar en `payload.sub` (estándar JWT) en TODOS los resolvers
de notifications.

✅ #3 COMMIT 6addd274 — aclaración (NO quitamos media-apiapp)
══════════════════════════════════════════════════════════════════════

Revisad de nuevo el diff de 6addd274:
  · Solo modificó resolveApiEventosOrigin() (HOST GRAPHQL).
  · NO tocó resolveImagesOrigin() (HOST IMÁGENES).
  · El bug que arreglaba: `/api/proxy/graphql` caía a NEXT_PUBLIC_IMAGES_BASE_URL
    como fallback → 502 (host de imágenes no sirve GraphQL).

`resolveImagesOrigin` SIGUE leyendo NEXT_PUBLIC_IMAGES_BASE_URL como primera
opción, que en .env.local y .env.production.local apunta a
media-apiapp.eventosorganizador.com. Por tanto el slug `/imgs/...` SIGUE
yendo a vuestro proxy R2 legacy.

PERO: hemos detectado que el fallback FINAL de resolveImagesOrigin caía a
DEFAULT_EVENTOS_ORIGIN (api-mcp). Eso podía romper imágenes en entornos sin
NEXT_PUBLIC_IMAGES_BASE_URL seteado. Fix defensivo aplicado en commit
ac1dae26 (HOY):

  Nueva const DEFAULT_IMAGES_ORIGIN = 'https://media-apiapp.eventosorganizador.com'

Ahora el fallback es explícito y correcto incluso sin env vars.
