Hola equipo api-mcp. Reporte de QA del 23-jun: el badge de notificaciones
en chat-ia muestra "63" sin notifs y al abrir el panel hay 0 items.
Es un mismatch entre dos resolvers vuestros que probablemente compartan
modelo pero NO el mismo filtro de tenant (whitelabel).

══════════════════════════════════════════════════════════════════════
SITUACIÓN
══════════════════════════════════════════════════════════════════════

Front llama DOS queries para pintar notificaciones (file:
apps/chat-ia/src/services/mcpApi/notifications.ts):

  Query A — badge:
    query { getUnreadNotificationsCount }
    → devuelve escalar Int (ej. 63)

  Query B — panel al abrir:
    query GetNotifications($filters: NotificationFilters, $pagination: CRM_PaginationInput) {
      getNotifications(filters: $filters, pagination: $pagination) {
        success total unreadCount notifications { ... }
      }
    }
    → devuelve { unreadCount: 0, notifications: [], total: 0 }

Ambas llamadas envían el header X-Development: bodasdehoy
(mcpClient.ts:7-12) Y el JWT del usuario (Authorization Bearer).

══════════════════════════════════════════════════════════════════════
HIPÓTESIS — resolver A no filtra por X-Development
══════════════════════════════════════════════════════════════════════

El resolver `getUnreadNotificationsCount` probablemente está haciendo:
  db.notifications.countDocuments({ userId, read: false })

Mientras que `getNotifications` filtra correctamente:
  db.notifications.find({ userId, development, read: false })

Resultado: el badge cuenta notifs de OTROS tenants donde el mismo userId
también tiene cuenta (super-admin de varias whitelabels), pero el panel
solo muestra las del tenant actual → mismatch 63 vs 0.

══════════════════════════════════════════════════════════════════════
LO QUE NECESITAMOS
══════════════════════════════════════════════════════════════════════

Que el resolver `getUnreadNotificationsCount` aplique el MISMO filtro
de tenant que `getNotifications`. Concretamente:

  Antes:
    countDocuments({ userId, read: false })

  Después:
    countDocuments({ userId, development, read: false })

  donde `development` se resuelve del contexto GraphQL (header
  X-Development o claim del JWT — el patrón que ya uséis en
  getNotifications).

LO QUE NO ES VUESTRO
══════════════════════════════════════════════════════════════════════

de nuestro lado hasta que el resolver corrija el filtro.

puesto, avisad y os mandamos un trace_id concreto + JWT decoded
para que rastreéis el caso (puede ser cache stale, índice
